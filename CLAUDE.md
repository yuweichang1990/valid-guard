# Valid Guard — Developer Instructions

> This file is for **contributors and AI assistants working on the Valid Guard codebase**. For user-facing documentation, see [README.md](README.md).

## Project Overview

Valid Guard is a Claude Code skill that provides **BDD-enhanced test design intelligence** — applying software testing theory (EP, BVA, DT, ST, PW, CE, EG) to generate risk-annotated YAML test plans, then producing Gherkin `.feature` files for the Cucumber BDD ecosystem. The skill definition lives in `.claude/skills/valid-guard/SKILL.md`.

### Architecture (Route C)

```
YAML Plan (design layer)  →  Gherkin .feature (executable layer)  →  Cucumber Runner (execution)
```

- **YAML plan** = risk, techniques, coverage tracking, decision tables, state machines
- **Gherkin .feature** = Given/When/Then executable specifications
- **Cucumber runner** = test execution (behave, cucumber-js, cucumber-jvm, etc.)

## Key Directories

```
.claude/skills/valid-guard/        — Skill definition (SKILL.md)
  ├── assets/                      — Report template, default config
  ├── references/                  — Techniques guide, YAML schema, anti-patterns
```

Note: `valid-guard/plans/`, `valid-guard/reports/`, `features/`, and step definitions are created at runtime in the **user's project**, not in this repository.

## Coding Conventions

- **Test plans**: Always YAML. Follow the schema in `.claude/skills/valid-guard/references/test-plan-schema.yaml`. Every scenario must have `name`, `type`, `risk`, `risk_rationale`, `techniques`, `gherkin_ref`, `status`, and `tags`.
- **Gherkin files**: `.feature` extension. Use Valid Guard tags for metadata: `@risk:high`, `@technique:ep`, `@technique:bva`, etc. Group by domain in `features/` subdirectories.
- **HTML reports**: Must work offline. No external CDN dependencies. Inline all CSS/JS.
- **Step definitions**: Language-specific, generated by `/vg generate`. Python uses behave; JS uses cucumber-js; Java uses cucumber-jvm.
- **File naming**: Plans use kebab-case (`user-auth.yaml`). Feature files use kebab-case (`user-authentication.feature`). YAML keys use snake_case (`risk_level`, `gherkin_ref`).
- **Risk levels**: `high`, `medium`, `low` only.
- **Risk rationale format**: `"Impact: X, Frequency: X, Consequence: X, Detectability: X. Average: X.XX → level."` — always include all 4 dimension names with numeric scores.
- **Scenario types**: `happy_path`, `edge_case`, `error_handling`, `boundary`, `security`, `state_transition`, `combinatorial`, `performance`.
- **Technique tags**: `equivalence_partitioning`, `boundary_value`, `decision_table`, `state_transition`, `pairwise`, `cause_effect`, `error_guessing`.

## Working on the Eval Suite

The benchmark suite is in `evals/`:

```bash
# Grade all 30 evals
make grade

# Generate HTML report
make report

# Verify all output files exist
make verify
```

Or directly:
```bash
cd evals
python grade.py baseline          # Grade + produce benchmark.json
python report_gen.py baseline/benchmark.json  # HTML report
python run.py --grade-only            # Alternative: grade via run.py
```

### Adding new eval cases
1. Add entry to `evals.json` with id, category, prompt, rubric
2. Add check patterns to `EVAL_CHECKS` in `grade.py`
3. Run the full suite to confirm no regressions

## Important Rules

- `valid-guard/reports/` (in the user's project) is gitignored
- When modifying the YAML schema, update both the schema file and DESIGN.md examples
- The HTML report focuses on **coverage gap analysis** — don't duplicate Cucumber's pass/fail reporting
- The HTML report uses export-to-JSON for round-trip editing: human edits in HTML → export JSON → AI reads JSON → updates YAML plan
- The YAML plan layer is language-agnostic — do not introduce language-specific logic into it
- Step definitions are language-specific — `/vg generate` handles this based on detected language and BDD framework
- BDD framework default is Cucumber (behave for Python, cucumber-js for JS, etc.)
